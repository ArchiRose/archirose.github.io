ARC-01Architecture

Microsoft Sentinel SOC architecture

Reference design

ToolsMicrosoft Sentinel · Log Analytics · Azure Monitor Agent · Logic Apps · ServiceNow

Key decisions

  • One workspace for every source, so one KQL query can join sign-ins, mail and endpoint data.
  • Every analytics rule is mapped to MITRE ATT&CK, which shows coverage gaps by tactic.
  • Automation enriches and tags incidents but never closes them. People decide outcomes.
  • 90 days of searchable data for investigations; older logs move to cheaper archive storage for audit.

Where it connects

  • The detection rules in SOC-01 and the enrichment playbook in SOC-02 run on this design in my lab.
  • Firewall logs arrive from the segmented network in ARC-03.
  • User-reported phishing from ARC-04 lands here as incidents.

ARC-02Architecture

Zero Trust sign-in with Conditional Access

Reference design

ToolsEntra ID · Conditional Access · Intune · Entra ID Protection

Key decisions

  • Each new policy runs in report-only mode for a week before it is switched on.
  • Two break-glass accounts sit outside every policy, with an alert on any use.
  • Admins sign in with phishing-resistant methods, because an ordinary MFA prompt can be relayed by a proxy phishing page (see ATK-01).

Policy set

CA05 Admin portals from compliant devicesAdmin directory rolesGrant: compliant device
Break-glass accountsTwo cloud-only accountsExcluded from every policy; any sign-in alerts the SOC

| where TimeGenerated > ago(1h)
| where FileName in~ ("vssadmin.exe", "wmic.exe", "wbadmin.exe", "bcdedit.exe")

Incident response runbooks

What to do, in order, and who does it. Phases follow NIST SP 800-61.

IR-01IR runbook

Ransomware on the network

Reference design
TriggerEDR ransomware alert, mass file renames, a ransom note, or shadow copies being deleted (ATK-02)
SeverityP1, critical
Example targetsConfirm in 15 minutes; contain within 1 hour
1Detect and analyse
  1. L1Confirm the alert: ransom note, changing file extensions, shadow-copy deletion.
  2. L1Scope it: which devices, accounts and file shares.
  3. L2Declare a P1, open the incident bridge and start the timeline log.
DecisionIs encryption still spreading?Yes: isolate the whole segment and disconnect backup targets now.No: contain device by device.
2Contain
  1. L1Isolate affected devices in Defender for Endpoint; the EDR stays connected.
  2. ITDisable compromised accounts and take affected shares offline.
  3. L2Block the attacker's IPs, domains and file hashes everywhere.
  4. L2Image memory and disk on the first infected host before any rebuild.
3Eradicate
  1. L2Find the way in (VPN, RDP or phishing) and close it.
  2. L2Remove persistence: new accounts, scheduled tasks, services, GPO changes.
  3. ITReset privileged credentials, including the KRBTGT account twice.
4Recover
  1. ITRebuild infected hosts and restore data from backups taken before the compromise.
  2. ITBring services back in priority order, scanning each restore.
  3. L1Watch restored systems closely for 30 days.
5After the incident
  1. DPODecide on reporting to the ICO within 72 hours if personal data is at risk.
  2. MgmtReport the crime: Police Scotland on 101, or Action Fraud in England, Wales and Northern Ireland. Tell the NCSC about significant incidents.
  3. L2Lessons-learned review within two weeks; add detections for anything missed.

Roles: L1 SOC analyst · L2 incident lead · IT operations · DPO data protection officer · Mgmt leadership. Any ransom decision sits with leadership and legal advisers, not the SOC.

SOC-01SOC

Sign-in, mailbox and endpoint detection rules

Built in my lab

MITRE ATT&CKT1110 Brute ForceT1078 Valid AccountsT1114.003 Email Forwarding RuleT1059.001 PowerShell

ToolsMicrosoft Sentinel · KQL · Entra ID sign-in logs · Office 365 audit log · Defender for Endpoint

  1. TriggerLogs arriveSign-in, Office 365 and endpoint process logs stream into the workspace
  2. EnrichScheduled queryEach rule runs hourly over the last hour of data
  3. DecideThreshold met?For example 10+ failures from one IP, then a success within 30 minutes
  4. ActCreate incidentAccount, IP and host mapped; MITRE tactic set
  5. RecordHand to triageAn automation rule starts the enrichment playbook (SOC-02)

What it does

Scheduled analytics rules in my Sentinel lab. They catch a run of failed sign-ins that ends in a success from the same IP address, a new mailbox rule that forwards or redirects mail, and PowerShell started with an encoded command. Each rule maps its account, IP and host entities so related alerts group into one incident and playbooks can act on them.

Guardrails

  • Rules alert only. Nothing is blocked automatically.
  • Thresholds sit in variables at the top of each query, so tuning is a one-line change.
  • Alerts group into one incident per account and IP, which keeps floods down.

What I'd measure

  • True positives per rule
  • Alerts per day per rule (noise)
  • Time from first failed sign-in to incident
Show the KQL 
// Rule 1: failed sign-ins followed by a success from the same IP  (T1110 -> T1078)
let failureThreshold = 10;
let window = 30m;
let failures = SigninLogs
    | where TimeGenerated > ago(1h)
    | where ResultType != "0"
    | summarize FailedCount = count(), LastFail = max(TimeGenerated)
        by UserPrincipalName, IPAddress, bin(TimeGenerated, window)
    | where FailedCount >= failureThreshold;
SigninLogs
| where TimeGenerated > ago(1h)
| where ResultType == "0"
| join kind=inner failures on UserPrincipalName, IPAddress
| where TimeGenerated between (LastFail .. LastFail + window)
| project SuccessTime = TimeGenerated, UserPrincipalName, IPAddress, FailedCount, AppDisplayName, Location

// Rule 2: new or changed inbox rule that forwards or redirects mail  (T1114.003)
OfficeActivity
| where TimeGenerated > ago(1h)
| where Operation in ("New-InboxRule", "Set-InboxRule", "UpdateInboxRules")
| where Parameters has_any ("ForwardTo", "ForwardAsAttachmentTo", "RedirectTo")
| project TimeGenerated, UserId, ClientIP, Operation, Parameters

// Rule 3: PowerShell launched with an encoded command  (T1059.001)
DeviceProcessEvents
| where TimeGenerated > ago(1h)
| where FileName in~ ("powershell.exe", "pwsh.exe")
| where ProcessCommandLine contains "-enc" or ProcessCommandLine contains "FromBase64String"
| project TimeGenerated, DeviceName, AccountName, ProcessCommandLine, InitiatingProcessFileName

Incident enrichment playbook

Built in my lab

ScopeEvery new Sentinel incident

ToolsMicrosoft Sentinel automation rules · Azure Logic Apps · VirusTotal API · Log Analytics

  1. TriggerIncident createdSentinel automation rule calls the playbook
  2. EnrichGet entitiesIP addresses, accounts and hosts from the incident
  3. EnrichCheck reputationVirusTotal lookup for each IP address
  4. DecideAny IP flagged?Malicious votes above the set level
  5. ActComment and tagSummary comment; tag 'enriched' or 'malicious-ip'
  6. RecordReady for triageContext is on the incident when the analyst opens it

What it does

When Sentinel opens an incident, an automation rule starts this Logic Apps playbook. It pulls the IP addresses and accounts out of the incident, checks each IP's reputation and writes one summary comment on the incident. The analyst opens the incident with the context already there.

Guardrails

  • Read-only. The playbook never closes an incident or changes its status.
  • The API key lives in Azure Key Vault, not in the workflow.
  • Runs under a managed identity with the Microsoft Sentinel Responder role and nothing wider.

What I'd measure

  • Time from incident creation to first analyst action
  • Share of incidents that arrive enriched
  • Lookups per day against the API quota

SOC-03SOC

Phishing triage and clean-up

Blueprint

MITRE ATT&CKT1566 Phishing

ToolsDefender for Office 365 · Microsoft Sentinel · Azure Logic Apps · VirusTotal · ServiceNow

  1. TriggerEmail reportedReport button or a Defender for Office 365 alert
  2. EnrichParse and extractSPF, DKIM and DMARC results, URLs, attachment hashes
  3. EnrichReputation checksURLs and file hashes checked in VirusTotal
  4. EnrichHunt the tenantKQL finds every recipient of the same message
  5. ApprovalAnalyst approvesVerdict: phish, spam or safe. Nothing is deleted without a click
  6. ActBulk clean-upSoft-delete matching messages; block sender and URL
  7. RecordClose the loopTicket updated; reporter told the verdict

What it does

Automates the phishing process I ran by hand on the SOC rota: read the headers, check the links and attachments, find everyone else who received the same email, then clean it up. The analyst decides the verdict. The automation does the collecting and the bulk actions.

Guardrails

  • Soft delete only, so a wrong call can be undone.
  • Clean-ups that touch more than 50 mailboxes need a second approver.
  • Feedback to the reporter uses a fixed template and never quotes the email.

What I'd measure

  • Time from report to verdict
  • Mailboxes cleaned per confirmed phish
  • Share of reports that were real phishing

SOC-05SOC

Vulnerability remediation tracker

Blueprint

PracticeVulnerability management

ToolsPython (pandas) · Scanner CSV export · CISA KEV catalogue · ServiceNow or GLPI

  1. TriggerWeekly scan exportCSV from the vulnerability scanner
  2. EnrichClean upDe-duplicate by host and CVE
  3. EnrichAdd contextAsset owner, and whether the CVE is known to be exploited
  4. DecideSet due dateFrom severity; sooner if actively exploited
  5. ActNotify ownersOne ticket per owner listing their open findings
  6. RecordWeekly reportOverdue findings by owner, and the trend

What it does

Turns a weekly scan export into a short list of who needs to fix what, and by when. Findings are de-duplicated, matched to an owner, checked against CISA's Known Exploited Vulnerabilities catalogue and given a due date from their severity.

Guardrails

  • Accepting a risk needs a named approver and an expiry date.
  • Known-exploited CVEs are always escalated, whatever their score.
  • Original scan files are kept unchanged for audit.

What I'd measure

  • Median days to fix, by severity
  • Overdue findings by owner
  • Known-exploited CVEs still open
Show the Python 
import pandas as pd

SLA_DAYS = {"Critical": 14, "High": 30, "Medium": 60, "Low": 90}   # example policy

scan = pd.read_csv("scan_export.csv")          # host, cve, severity, first_seen
kev = set(pd.read_csv("known_exploited_vulnerabilities.csv")["cveID"])

findings = scan.drop_duplicates(["host", "cve"]).copy()
findings["kev"] = findings["cve"].isin(kev)
days = findings["severity"].map(SLA_DAYS).where(~findings["kev"], 7)   # exploited: 7 days
findings["due"] = pd.to_datetime(findings["first_seen"]) + pd.to_timedelta(days, unit="D")

overdue = findings[findings["due"] < pd.Timestamp.today()]
print(overdue.groupby("host").size().sort_values(ascending=False))
